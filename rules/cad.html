FreeCAD on the GMKtec: one binary

  • 🛑 Run FreeCAD only as ~/.local/bin/FreeCAD-weekly-2026.11.11 (the 27.1 dev weekly). The 1.1.1 binary, ~/.local/bin/FreeCAD, is banned for every session (operator 2026-11-16: "you are everybody's banned from using the old FreeCAD version. Switch to the new FreeCAD version.").
  • Bare FreeCAD on the GMKtec's PATH is the banned binary. Wherever a doc or a script says FreeCAD -c …, call the weekly binary by its full path.
  • While a CAD build is running on the GMKtec, 3D Printing starts no FreeCAD run there (operator 2026-11-16).
  • Once CAD has built and gated a part, 3D Printing runs no FreeCAD on that part (operator 2026-11-16: "You should not be running FreeCAD builds after that on the same thing."). Its work on that part is the Python book rebuild and the 3MF and mesh gates; CAD's gate lines are quoted from CAD's push.

Who runs which build

One FreeCAD build at a time on the GMKtec (operator 2026-11-16, to the CTO: "CAD runs all builds except for cradles, which Print3D runs ... only one run a build at a time ... Print3D is also responsible for preparing the books. Karma's job is to just check the books. That's it.").

  • CAD builds everything except the cradle family: fence, carrier, wired bay, wand, full assemblies. The full-assembly run is CAD's as one job; its cradles stage hangs 3D Printing's cradle parts at HEAD and rebuilds none.
  • 3D Printing builds every BigClaw cradle part (cradle, L, catch, A-back, coupons) and prepares both print books.
  • Karma checks the print books only: slicer gates, settings tables, live printer reads, and tells the operator a plate is ready. No FreeCAD, on any machine.
  • Full assemblies are idle-time work (operator 2026-11-16): they run when the GMKtec has nothing else to do, yield to any part or book build, and are never a gate on releasing a part or a plate. The wired-bay assembly is not in that class; it is a deliverable the operator wants to see.

The OCC shim is not FreeCAD

  • cad/exports/BUILD_STAMP.json must read "builder": "freecad" before anything is printed. occ_shim means faceted thread flanks — viewing and checking only.
  • Never commit shim exports as production geometry without the --builder=occ_shim stamp that marks them as such.
  • ⛔ A shim run must never overwrite a real FreeCAD output/. Both builders write that directory and the shim's geometry is strictly worse. Check whether anyone has regenerated since your run started, before committing.
  • Exit 0 means nothing. FreeCAD -c exits 0 even when a macro logs === RESULT: FAIL — N thread cut(s) did not apply ===. Grep every macro's === RESULT: line, and the gate fit_checks_wand_flashlight.py must end === FIT RESULT: PASS ===. A gate that cannot fail is not a gate. check_exports_fresh.py --update now refuses to stamp when a lumi_wand_*_diag.txt (in the OS temp dir, tempfile.gettempdir()) says OVERALL_OK=False. ⛔ Read "/tmp/lumi_wand__diag.txt" until 2026-10-10.* Full procedure: cad/freecad/REGENERATE.md.
  • 🚨 A head ring printed from a 2026-09-23 → 09-30 export has NO THREAD. Reprint it. The freshness check passed on it: the exports were byte-identical to HEAD and threadless in both. "Current" is not the same as "correct".
  • Measuring threaded parts: common() volumes lie — a solid lip can report 0.0, and overlaps can come out negative. Verify ring fit by point-sampling with isInside, kept light (~24 angles × 0.25 mm in Z); dense runs blow the 30-minute background limit.
  • Under FreeCAD -c, stdout is lost unless you call sys.stdout.reconfigure(line_buffering=True), and scripts that use __file__ (the cartridge macro, the gates) need __file__ injected before exec().
  • Layer-2 fit checks read the exported STEPs, which are LFS pointers on a fresh clone. Fetch them with one -I per git lfs pull — a multi--I invocation silently fetches nothing and the gate dies on a parse error.
  • check_exports_fresh.py cannot run on the Windows box — it imports the shim, which needs OCP. Verify export freshness on the GMKtec, or trust BUILD_STAMP.json plus the LFS integrity check.

Wand geometry that gets misremembered

  • Threads are M72×3 top AND bottom since 2026-10-15 (v9.13: the head moved to M72 on a raised collar so its seat rim is a 2.05 mm wall like the end's). Head ring + end ring + retaining ring all share the M72 form. ⛔ Read "M70×3 top (head ring), M72×3 bottom" until 2026-10-15; anything saying M64/M66 is pre-v9.8.
  • 🔴 The retaining ring and the end ring interfere, so never both on the wand's bottom thread. A full flashlight does use both: the retaining ring at the wand/extension joint, and an end plate + end ring as the tail cap on the extension's own Ø72 peg.
  • The extension macro exports BOTH LCD variants in one run (for lcd_type in ("lilygo", "waveshare")). You do not flip LCD_TYPE and re-run — the comment at the top of the macro saying so is stale. The facets still are not interchangeable: print the halves whose filename suffix matches your display.
